## Общие замечания

### 1. 🟠 Предупреждение — Демо проверяют разные копии библиотеки

**Файл:** `demo/eventSignals-test-app/package.json`, строки 19.

**Проблема:** Лаборатория импортирует исходники корневого проекта, а clicker — свою скомпилированную копию:
`demo/clicker/logic/activeRoundsStore.ts`, строка 7,
`import { EventSignal } from "../modules/EventEmitterX/EventSignal";`. Поэтому успешный запуск clicker не проверяет
последнюю реализацию EventSignal в корне. Это не основание редактировать сгенерированные копии напрямую.

```json
"@termi/eventemitterx": "link:../../"
```

**Рекомендация:** Определить общий источник сборки и воспроизводимый шаг генерации копий либо перевести демо на
публичные entry points, когда это позволит roadmap упаковки/зависимостей. Показывать версию/коммит библиотеки в панели
разработчика. После работ по публикации добавить запуск потребителя пакета; сохранить отложенный запрет на изменение
внутренних packages.

### 2. 🟠 Предупреждение — Проверки сборки имеют разный смысл

**Файл:** `demo/eventSignals-test-app/package.json`, строки 11.

**Проблема:** Сборка лаборатории выполняет bundling без проверки типов. Clicker объявляет `tsc -b && vite build` в
`demo/clicker/frontend/package.json`, строка 12; его bundler прошёл, но проверка типов упала. Если написать для обоих
просто «сборка проходит», блокирующая проблема останется скрытой.

```json
"build": "vite build"
```

**Рекомендация:** Для обоих приложений предоставить отдельные команды typecheck, test, bundle и preview-smoke, затем
составить обязательную проверку релиза из всех необходимых шагов. Использовать подходящие для браузера границы проектов
и явно учитывать известные корневые диагностики вместо их сокрытия. Проверять чистую установку на задокументированной
версии Node/package manager, а также запуск Windows и Unix.

### 3. 🟠 Предупреждение — У clicker нет штатного запуска с изолированными данными

**Файл:** `demo/clicker/backend/prisma/schema.prisma`, строки 5–8.

**Проблема:** Путь SQLite фиксирован; `demo/clicker/backend/src/orm/prismaClient.ts`, строка 5, создаёт
`new PrismaClient()` без переопределения. Для этой проверки потребовался временный bootstrap, задающий datasource копии
базы. Обычные ручные smoke-тесты иначе записывают данные в существующую демонстрационную базу.

```prisma
datasource db {
  provider = "sqlite"
  url      = "file:./data/dev.db"
}
```

**Рекомендация:** Добавить явную настройку URL базы и локальную команду fixtures/reset. Отделить одноразовые тестовые
данные от существующих пользовательских данных и production-конфигурации. Приёмка: одна задокументированная команда
запускает изолированное демо, создаёт известных пользователей разных ролей и раунды, позволяет пересоздать тестовую базу
без изменения сохранённого исходного файла.

Использовать общий визуальный язык, сохраняя исследовательский характер лаборатории и игровой фокус clicker. Добавить
короткий блок «что демонстрирует пример» со ссылкой на исходник, ожидаемым результатом и сбросом. Счётчики рендеров,
stack trace и симуляции вынести в опциональную панель разработчика. Посетителю показывать короткие ошибки с действием,
подробную диагностику — в панели.

При декомпозиции сначала выделять связные обязанности: счётчики/пользовательские данные, async-поиск и
представление/состояние мирового времени в лаборатории; авторизацию, команды раундов, время и жизненный цикл SSE в
clicker. Сохранять Git-историю при переносе существенной реализации по принятому процессу декомпозиции; для новых
простых файлов типов допустимо ранее разрешённое исключение.

## Проверки, которые следует добавить

Автоматизировать значимые контракты: первый вход; writable/computed-обновления; pending/error/retry и устаревшие
async-результаты; освобождение общих сигналов; границы времени раунда; последовательная/конкурентная идемпотентность;
клавиатурная активация; восстановление после пропущенных событий; повторное монтирование клиента и рестарт сервера.
Использовать одноразовые данные, управляемое время там, где нужно, и количество подписок/запросов для проверки
жизненного цикла.

До признания демо готовыми к релизу выполнить чистую установку, полную сборку, production preview с перезагрузкой по
прямому вложенному адресу, проверки разных браузеров, backend-тесты, несколько клиентов с разрывом/восстановлением SSE,
рестарт сервера с незавершёнными раундами и измеренный тест памяти/жизненного цикла. Эти проверки в данном обзоре не
завершены. Переключение локали, все варианты игры, разрешения Picture-in-Picture и доступность провайдера погоды
полностью не проверялись. Настольный интерфейс осмотрен визуально; явное измерение 390 px выполнялось только для
clicker.

## Команды воспроизведения

Из соответствующих каталогов, с установленными зависимостями:

```powershell
# demo/eventSignals-test-app
node node_modules/vite/bin/vite.js --host 127.0.0.1 --port 5181 --strictPort
node node_modules/vite/bin/vite.js build --outDir ../../build_cache/demo-signals-dist

# demo/clicker/frontend
$env:VITE_BACKEND_PORT='3101'
node node_modules/vite/bin/vite.js --host 127.0.0.1 --port 5182 --strictPort
node ../../../node_modules/typescript/bin/tsc -b --pretty false
node node_modules/vitest/vitest.mjs run
node node_modules/vite/bin/vite.js build --outDir ../../../build_cache/demo-clicker-dist
```

Backend запускался изолирующим bootstrap проверки, а не обычным скриптом `dev`. Не следует считать, что одно значение
`DATABASE_URL` изолирует текущую Prisma-схему с фиксированным путём. Штатный изолированный запуск предложен выше.
