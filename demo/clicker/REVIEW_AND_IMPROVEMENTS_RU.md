# Clicker: проверка и улучшения

[English version](REVIEW_AND_IMPROVEMENTS.md) · [Общие рекомендации](../RECOMMENDATIONS_RU.md).

## Назначение и оценка

Приложение демонстрирует авторизованную игру в реальном времени с командами разных ролей, async-интерфейсом EventSignal,
таймерами, пакетированием кликов и SSE-обновлениями. Проверенный раунд одного игрока работает от начала до конца.
Воспроизведённые ошибки API и заблокированный typecheck следует исправить до расширения игры или использования
приложения как шаблона реализации.

Контекст проверки: `dev` / `b943225`, 2026-10-06; Node 26.8.1, TypeScript 5.9.3, Vite 6.3.5 и существующие зависимости.
Frontend работал на `http://127.0.0.1:5182`, backend — на `http://localhost:3101`. Игнорируемая копия SQLite и временный
секрет подписи изолировали все тестовые записи. Текущий clicker использует собственную скомпилированную копию
EventSignal.

## Замечания и рекомендации

### 1. 🔴 Критично — Регистрация выдаёт права администратора по имени

**Файл:** `demo/clicker/backend/src/auth/authService.ts`, строки 72–80.

**Проблема:** Подтверждено на изолированной базе: регистрация без авторизации с именем `admin` возвращает роль ADMIN.
Это поддерживает исходный сценарий демонстрации для интервью, но при использовании endpoint в настоящем приложении
становится повышением привилегий.

```typescript
const role: UserRole = (name === 'admin' || name === 'test_admin')
    ? 'ADMIN'
    : name.toLowerCase() === 'никита'
        ? 'USER_HIDE_TAPS'
        : 'USER';
```

**Рекомендация:** Отделить подготовку демонстрационных пользователей от публичной регистрации. Регистрация должна
выдавать USER независимо от имени. Создавать администратора и пользователя со скрытыми кликами отдельной локальной
seed-командой в явно обозначенном demo-режиме. Приёмка: имена `admin` и `test_admin` не повышают роль при публичной
регистрации; тестовые пользователи продолжают демонстрировать различие ролей.

### 2. 🔴 Критично — Повторные запросы создают дубликаты раундов

**Файл:** `demo/clicker/backend/src/routerHandlers/roundsRouters.ts`, строки 122–123, 245–246.

**Проблема:** Два последовательных POST-запроса с одинаковым `X-Idempotent-Id` создали разные ID раундов. Fastify/Node
приводит имена входящих заголовков к нижнему регистру, а чтение использует смешанный регистр. То же чтение применяется
для кликов, поэтому защита от повторов там тоже под угрозой; повторное начисление кликов отдельно не проверялось.

```typescript
const idempotentId = String(req.headers["X-Idempotent-Id"] || '');
const alreadyHandledResult = (idempotentId && requestsIdempotentMap.get(idempotentId)) || void 0;
```

**Рекомендация:** Читать `x-idempotent-id`, проверять формат и включать в ключ пользователя, операцию и ресурс. Хранить
атомарное резервирование/результат со сроком действия и идентичностью тела запроса; один локальный Map результатов не
предотвращает одновременные повторы или повторы после рестарта. Для постоянных операций предпочесть уникальный ключ
БД/транзакцию. Приёмка: последовательные и одновременные повторы возвращают один раунд или результат клика; другой
пользователь не получает чужой кешированный ответ.

### 3. 🔴 Критично — Фильтр активных раундов выбирает истёкшие раунды

**Файл:** `demo/clicker/backend/src/routerHandlers/roundsRouters.ts`, строки 60–65.

**Проблема:** Подтверждено на только что созданном действующем раунде: `/rounds` его возвращает, а
`/rounds?isActive=true` — нет. Условие требует дату окончания раньше текущего времени, что противоположно
продолжающемуся раунду.

```typescript
where: isActive ? {
    completed: false,
    endedAt: {
        lt: new Date(),
    },
} : void 0,
```

**Рекомендация:** Определить отдельные состояния: запланирован, идёт, завершён. Если active означает текущий раунд,
использовать `startedAt <= now`, `endedAt > now` и `completed=false`; если сюда включены будущие раунды, убрать условие
начала и явно назвать/описать контракт. Использовать одно зафиксированное серверное время и проверить обе временные
границы и явное завершение.

### 4. 🟠 Предупреждение — Штатную сборку блокируют общие типы и конфигурация

**Файл:** `demo/clicker/frontend/tsconfig.node.json`, строки 24–26.

**Проблема:** `tsc -b` завершается TS18003, поскольку include не совпадает с `vite.config.ts`. Также обнаружены
недоступные Prisma-типы, неправильные импорты типов и неустранимый синтаксис общих модулей. Связанные места:
`demo/clicker/api/routers.ts`, строки 3–6 (`import { User, Prisma, Round, UserRole } from '@prisma/client';`);
`demo/clicker/frontend/tsconfig.app.json`, строки 13 и 22 (`verbatimModuleSyntax: true`, `erasableSyntaxOnly: true`).
Прямая Vite-сборка проходит, но это не подтверждает корректность типов.

```json
"include": [
    "vite.config"
]
```

**Рекомендация:** Исправить include; явно оформить импорты только типов. Выделить безопасные для браузера DTO отдельно
от типов реализации ORM, чтобы frontend не зависел от разрешения backend-установки Prisma. Явно решить, компилируются ли
общие enum или заменяются устранимыми константами/типами; не отключать строгость целиком. Приёмка: задокументированный
`pnpm build` проходит после чистой установки и проверяет общую границу.

### 5. 🟠 Предупреждение — Текущая подготовка тестов падает на Node 26

**Файл:** `demo/clicker/frontend/src/tests/layouts/AppLayout.test.tsx`, строки 30–34.

**Проблема:** На Node 26.8.1 прошли 49 frontend-тестов, а все пять тестов AppLayout упали до проверок: глобальный
`localStorage` оказался undefined. Vitest использует jsdom, но обращение к хранилищу через глобальное имя в этом runtime
ненадёжно. Результат зависит от среды; хранилище самого приложения в браузере работало.

```typescript
beforeEach(() => {
    vi.clearAllMocks();
    localStorage.clear();
});
```

**Рекомендация:** Явно использовать хранилище окна jsdom и при необходимости централизованно настроить глобальное имя в
setup с определённым origin документа. Зафиксировать и описать поддерживаемую версию Node; проверку другого runtime
добавлять только при соответствующем объёме поддержки. Приёмка: проходят все 54 теста, включая сохранённую светлую тему
при тёмной теме ОС.

### 6. 🟠 Предупреждение — Искусственные ошибки включены в обычном сценарии

**Файл:** `demo/clicker/logic/activeRoundsStore.ts`, строки 66–67, 85–88.

**Проблема:** Наблюдалось сразу после входа и снова после перезагрузки страницы. Retry восстанавливает работу, то есть
boundary работает, но новый посетитель сначала видит сломанный dashboard. Искусственная двухсекундная задержка в
`demo/clicker/backend/src/routerHandlers/roundsRouters.ts`, строка 56 (`await promiseTimeout(2000);`), также действует
на каждый запрос списка.

```typescript
const showErrorOnFirstTry = localStorage.getItem('DO_NOT_THROW_ERROR_ON_FIRST_TRY') !== 'true';
// ...
if (showErrorOnFirstTry && !wasErrorOnFirstTry) {
    wasErrorOnFirstTry = true;
    throw _makeFakeError();
}
```

**Рекомендация:** Предоставить явную панель симуляции ошибок с детерминированными сценариями и сбросом. По умолчанию
открывать успешный сценарий; задержки/ошибки включать настройками демо, не влияющими на обычный production-режим.
Добавить понятные состояния пустого списка, загрузки и отсутствия сети; при переподключении сохранять последние успешные
данные.

### 7. 🟠 Предупреждение — Dashboard выходит за границы мобильного экрана

**Файл:** `demo/clicker/frontend/src/signalComponents/RoundsList.css`, строки 2–18.

**Проблема:** Подтверждено при 390 × 844: ширина документа 719 px, выбранный раунд большей частью находится за экраном,
а Logout обрезан. Постоянная двухколоночная компоновка сочетается с крупными датами и ASCII-областью кликов
фиксированной ширины.

```css
.cards-page { display: flex; flex-direction: row; }
.cards-list { width: 20%; min-width: 190px; }
.selected-card-container { padding-left: 16px; flex-grow: 1; }
```

**Рекомендация:** На определённом breakpoint складывать список и детали вертикально, задать `min-width: 0` гибкому блоку
деталей, переносить навигацию и заменить ASCII-графику масштабируемой иллюстрацией внутри кнопки действия. Сделать даты
второстепенными, высоту карточки — гибкой. Приёмка: при 390 px нет горизонтальной прокрутки документа; выбор раунда,
клики и выход доступны при масштабе 200%.

### 8. 🟠 Предупреждение — Главное игровое действие доступно только указателем

**Файл:** `demo/clicker/frontend/src/signalComponents/SelectedRound.tsx`, строки 148–153.

**Проблема:** Дерево доступности показывает контейнер вместо кнопки действия. Клик указателем увеличивает оба
отображаемых счёта, но элемент не имеет нативного фокуса и активации через Enter/Space.

```typescript
<div className="selected-card-clicker" data-round-id={id}
    onClick={onSelectedCardClicked}
>
    <span>Кликайте сюда</span>
```

**Рекомендация:** Использовать нативную кнопку с понятным именем, видимым фокусом и ID раунда, необходимым обработчику.
Сохранить серверную проверку и существующую синхронизацию счёта. Показывать cooldown/недоступность текстом, не объявлять
каждый частый клик. Приёмка: авторизованный игрок получает балл клавиатурой и не может кликать завершённый раунд.

### 9. 🟠 Предупреждение — Сохранённая светлая тема игнорируется при тёмной теме системы

**Файл:** `demo/clicker/frontend/src/layouts/AppLayout.tsx`, строки 27–29.

**Проблема:** Статическая проверка: сохранённое `"false"` приводит к использованию системной темы, поэтому тёмная тема
ОС заменит явно выбранную пользователем светлую тему при следующем монтировании. Браузерный сценарий с тёмной системной
темой не запускался.

```typescript
const savedMode = localStorage.getItem(_localStorage_darkMode_key);
return savedMode && savedMode === 'true' ? true : _detectBrowserDarkMode();
```

**Рекомендация:** Различать отсутствие значения и сохранённое булево значение либо описать тему как system/light/dark.
Применять настройку одинаково на странице входа и в layout приложения; проверить повторное монтирование и изменение
системной темы.

### 10. 🟡 Предложение — Настройки открывают стартовую страницу Vite

**Файл:** `demo/clicker/frontend/src/App.tsx`, строки 26.

**Проблема:** Подтверждено в браузере: Settings показывает логотипы Vite/React, образец счётчика и инструкции HMR.
Profile показывает только имя пользователя. Эти маршруты пока не помогают игроку понять или настроить игру.

```typescript
<Route path="/settings" element={<DemoPage />} />
```

**Рекомендация:** Заменить Settings настройками темы, языка, уменьшения анимации и учебных сценариев; при необходимости
скрыть маршрут до готовности. Дополнить Profile личной историей раундов и счётом. Добавить легенду состояний раунда,
правила и объяснение начисления очков; дать администратору настройки длительности/cooldown в диалоге создания. Убрать
постороннее оформление шаблона.

### 11. 🟠 Предупреждение — JWT-секрет имеет сохранённое в коде значение по умолчанию

**Файл:** `demo/clicker/backend/src/common/env.ts`, строки 12.

**Проблема:** Статическая проверка: при отсутствии конфигурации каждая установка незаметно использует один и тот же ключ
подписи из репозитория. В примере значение намеренно опущено. Backend для проверки использовал временный случайный
секрет. Для размещённого сервиса такой fallback небезопасен, хотя текущая проверка выполнялась локально.

```typescript
export const JWT_SECRET = process.env.JWT_SECRET || /* committed fallback literal */;
```

**Рекомендация:** Останавливать запуск без внешнего секрета вне явно включённого одноразового demo-режима. Описать
локальную настройку без настоящих секретов; генерировать локальный секрет для тестовых пользователей. Ограничить
development CORS вне этого режима и добавить валидацию схем/ограничение частоты запросов авторизации перед публичным
размещением.

## Направление дизайна

Сосредоточить dashboard на выбранном раунде: состояние, оставшееся время, счёт и одна большая доступная кнопка клика.
Даты и техническую диагностику сделать второстепенными. Заменить тяжёлые рамки и чрезмерно крупные даты одинаковыми
карточками, отступами и короткими обозначениями состояния. Использовать читаемый отсчёт с доступным описанием прогресса;
отрицательный процент не должен быть основным объяснением для пользователя.

На мобильном показывать компактный выбираемый список над деталями. Держать основное действие доступным и различать
отправляемые клики и подтверждённый счёт. Показывать состояния «подключение / live / переподключение / offline», чтобы
остановившийся счёт был понятен. Объяснять cooldown и начисление до первого раунда, а не через ошибки. Использовать
согласованные RU/EN-подписи и содержательный title документа.
