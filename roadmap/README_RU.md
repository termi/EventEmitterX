# Roadmap EventEmitterX / EventSignal

Дата аудита: 2026-10-05. Статус: план утверждённого направления, реализация этапов не начата в рамках аудита. Обновление
соответствия документации: 2026-10-06.

Цель: независимо устанавливаемая библиотека событий и сигналов с надёжным lifecycle, точными типами, CJS/ESM и
TypeScript-исходниками, отдельными опубликованными зависимостями и понятным контрактом для потребителя.

### Результат реализации — 2026-10-06

Reducer обычного записываемого сигнала теперь получает последнее принятое значение в `prev` без обязательного `get()`.
Для computed-сигналов `prev` остаётся последним выходным значением, а `sourceValue` — последним принятым исходным;
запись source не вызывает принудительное вычисление. Сохранены срабатывание throttle и расписание уведомлений в microtask.
Реализация находится в `modules/EventEmitterEx/EventSignal.ts`, строки 1421–1428.

Двенадцать регрессионных случаев охватывают записи без наблюдения, чтение, границы microtask, подписки и объединение
уведомлений, literal/null/zero, неизменяемые объекты и data, undefined и ошибки, синхронный/асинхронный computed
output, ленивость mapped, throttling и изоляцию зависимостей. Все тесты EventSignal проходят. Полный набор содержит
364 успешных теста, прежние 14 сбоев в `events_spec`, один пропущенный тест и шесть todo.
Строгая проверка библиотеки сохраняет 36 диагностик. Закрыт пункт предложения 01.3 (контракт записываемого reducer),
а не третья галочка этапа 01 о разделении runtime-проверок и проверки типов.

Далее: [задача 03.1 — автоматический вывод типов сигнала](03_API_TYPES_RU.md#031--следующий-пункт-автоматический-вывод-типов-сигнала).
Простой async-конструктор уже выводит типы; фабрика и контекстный вывод self требуют согласованного исправления.

Следующий раздел сохраняет свидетельства до исправления; закреплённая копия Junction ORM не изменялась.

#### 🟠 Предупреждение — последовательные reducer теряют инкременты без промежуточного чтения

**Файл:** `modules/EventEmitterEx/EventSignal.ts`, строки 1426 и 1447–1449 (снимок до исправления).

**Проблема:** `set` получает первый аргумент reducer через `_innerGet()`, а второй — из `_sourceValue`.
В закреплённой интеграции Junction ORM (`junct.io` / `f3bb99e2b4c34152de74dc5b04885122e3880fde`) первый аргумент остаётся устаревшим
при последовательных записях без наблюдателя. Поэтому чтение потребителем меняет результат работы счётчика.
Владелец считает такое поведение нелогичным и просит включить его в первые кандидаты на рефакторинг.
Эксперимент ниже выполнен на закреплённой интеграции; регрессионные тесты также воспроизвели проблему локально до исправления.

```ts
const currentValue = this._innerGet();
const { _sourceValue } = this;
const currentSourceValue = (_sourceValue !== void 0 ? _sourceValue : currentValue) as S;
const _newSourceValue = (newSourceValue as ((prev: T, sourceValue: S, data: D) => S))(
    currentValue as T, currentSourceValue, this.data,
);
```

```ts
const changes = EventSignal.createSignal(0);
changes.set(prev => ++prev);
changes.set(prev => ++prev);
changes.set(prev => ++prev);
changes.get(); // Наблюдаемый результат: 1. Ожидаемый: 3.
```

**Рекомендация:** Reducer обычного записываемого сигнала должен получать последнее принятое значение независимо
от промежуточных вызовов `get()` или подписок. Сохранить ленивое вычисление производных сигналов и различие исходного
и вычисленного значений у mapped-сигналов; отдельно определить их контракт reducer, а не заменять `prev` повсеместно.
Временное решение в Junction ORM — `set((_prev, sourceValue) => ++sourceValue)`; оно не должно быть обязательным для
обычного счётчика.

**Проверки приёмки:** Три инкремента дают `3` без чтения, с промежуточным чтением, с подписчиком и с переходом между
microtask. Добавить случаи mapped/computed-сигналов, разных типов исходного и выходного значения и ошибок reducer.
Отдельно проверить расписание уведомлений и ленивость: объединение callback не должно терять инкременты.
Откладывание исправления создаёт риск неверных счётчиков ревизий и накопленного состояния с результатом,
зависящим от наблюдения.

## Зафиксированные решения владельца

- Корневой индекс реэкспортирует все публичные библиотечные модули проекта. `EventEmitterX` имеет алиас `EventEmitter`;
  степень совместимости с `node:events` нужно доказать аудитом. Тестовые экспорты и внутренние детали не становятся
  публичным API автоматически.
- Нужны CJS и ESM (`.mjs`), а также доступ к TypeScript-исходникам для Bun/Deno. Будущие build-configs реализовать, а не
  удалять намерение нескольких сборок.
- Локальные `link:` зависимости намеренны на этапе разработки. В этой сессии предстоит восстановить/оформить независимые
  пакеты и подготовить их публикацию. Запрет на редактирование `packages/` остаётся; его пересмотр отложен до этапа
  развития зависимостей.
- Перегрузки `createSignal` требуют завершения.
- Декомпозиция больших модулей **обязательна с сохранением git-истории**. Метод и проверка описаны в этапе 04.
- Известная утечка EventSignal из-за глобальных регистров — отдельный P0. Одного требования вызывать `destructor`
  недостаточно для исправления архитектуры.
- WEATHER_INTEGRATION_PLAN включён в этап 09; оригинальные документы сохранены.
