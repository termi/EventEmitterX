# Каналы уведомлений сигналов: три альтернативы

## Реализации и решение

`dev` сохраняет первый вариант. Второй вариант и прототип списка сохранены в
`experiment/eventsignal-instance-channels`, коммит `d17917f2518a7b3a0700131b2076a949fdb0ae89`, без слияния в `dev`.
Этот документ и исходные замеры сохранены в `dev` как доказательства; экспериментальный код и бенчмарк не перенесены.

Первый вариант закоммичен в `686c0d19603b447a8b31ead6552b705c60acafca`: три глобальных для модуля
канала EventEmitterX со слабыми callbacks. Второй вариант заменяет эти emitter каналами, принадлежащими сигналам;
callbacks и обратные операции отключения остаются слабыми. Каналы создаются лениво. Автоматическая сборка проверена
для обоих вариантов; второй меняет архитектуру владения, а не повторно объявляет первый протекающим.

Третья альтернатива — исполняемый прототип канала на двусвязном списке в `_dev/compare_signal_channels.cjs`,
с Map от идентичности callback к узлу списка. Это кандидат для сравнения, а не интегрированная реализация EventSignal.

| Аспект                 | Вариант 1: глобальные каналы                                             | Вариант 2: каналы экземпляров                                                                   | Прототип списка                                                                                              |
|------------------------|--------------------------------------------------------------------------|-------------------------------------------------------------------------------------------------|--------------------------------------------------------------------------------------------------------------|
| Владение               | Модуль владеет хранилищем listeners; владельцы хранят исходные callbacks | Сигнал владеет ленивым хранилищем; обратные связи слабые                                        | Владелец должен владеть списком; при интеграции нужно добавить такое же слабое владение                      |
| Доставка               | Поиск в глобальном emitter по символу сигнала                            | Прямой канал источника, символ локален для канала                                               | Обход списка источника                                                                                       |
| Забытый владелец       | Слабые callbacks разрешают сборку; финализатор удаляет глобальные записи | Собственные каналы собираются с владельцем; финализатор отключает исходящие/внешние регистрации | Сам список не решает удержание; узлы не должны сильно владеть зависимыми сигналами                           |
| Неиспользуемый сигнал  | Нет собственного контейнера каналов                                      | Один небольшой контейнер, без emitter                                                           | Потребуется ленивый контейнер списка                                                                         |
| Удаление               | Существующая реализация EventEmitterX                                    | Та же реализация emitter                                                                        | Поиск в Map плюс O(1) отключение узла; расходы Map/узлов сохраняются                                         |
| Изменения при доставке | EventEmitterX копирует при изменениях, а не при каждом emit              | То же поведение                                                                                 | Прототип снимает snapshot при каждом emit; вариант без snapshot требует дополнительной работы над семантикой |
| Совместимость          | Существующее поведение once/prepend/дедупликации                         | Сохраняет тот же emitter и публичный API подписок                                               | Только точечные проверки порядка/дедупликации/удаления/once/вложенного once; не полный API emitter           |

Владелец решил оставить первый вариант активным, а второй сохранить отдельно для возможной будущей работы.
Локальное владение пока не компенсирует измеренные затраты памяти без устойчивого выигрыша скорости полного графа.
Не заменяем рабочие каналы прототипом списка только на основании микробенчмарков. Будущий компактный канал может
сохранить владение экземпляром и специализировать случай одного listener; для этого нужны отдельные проверки
поведения и runtime.

## Методика и воспроизведение

Из корня репозитория в checkout `experiment/eventsignal-instance-channels` (в `dev` скрипта нет):

```powershell
node --expose-gc _dev/compare_signal_channels.cjs
node --expose-gc _dev/compare_signal_channels.cjs core phase1
node --expose-gc _dev/compare_signal_channels.cjs core phase2
node --expose-gc _dev/compare_signal_channels.cjs channels linked
```

Полная команда чередует порядок реализаций и запускает по пять замеров каждого варианта в новых процессах.
Базовый вариант читается через `git show`; оба исходника используют один экземпляр ts-node и одинаковые параметры
компилятора проекта. Ветка и рабочее дерево не изменяются. Базовый коммит должен быть доступен локально.
Среда: Node v26.8.1, Windows x64, TypeScript 5.9.3. Исходные замеры и данные CPU находятся в
[signal-channel-results.json](signal-channel-results.json).

Замеры полного ядра включают 4 000 неиспользуемых сигналов, предельный прирост heap ещё для 1 000 computed-сигналов
с подписчиком у каждого и 200 обновлений для 1 000 активных computed-сигналов после 30 прогревочных обновлений.
Проверяется итоговое значение каждого computed-сигнала. В этой нагрузке чтения не публикуют адреса совместимости.

Замеры каналов включают 10 000 каналов с одним слабым callback и живым владельцем callback у каждого, 1 000 000
доставок, 200 000 пар remove/add и 20 000 emit с 64 слабыми callbacks. Адаптеры глобальных каналов используют один
emitter; адаптеры экземпляров создают отдельные emitter. Значения heap включают адаптеры, исходные callbacks, WeakRef
и структуры регистрации; это не размеры отдельных объектов. Перед замерами каналов выполняются точечные сравнительные проверки.

Значения — медианы; в скобках приведены наблюдавшиеся минимум–максимум по пяти процессам.

Расход на неиспользуемого владельца вырос примерно на 36 байт (1,2%); на активного — на 544 байта (12,7%). Медиана
обновлений выше на 4,8%, но диапазоны пересекаются: эксперимент не доказывает устойчивого ускорения или
статистически значимой регрессии. Выигрыш микробенчмарков не переносится напрямую на весь граф.

Прототип списка компактен и конкурентоспособен для одного listener, но выделение snapshot проигрывает EventEmitterX
на 64 listeners в этом запуске. Удаление в списке и emitter зависит от реального хранилища и правил изменений;
отключение узла за O(1) не делает каждую операцию подписки быстрее. Для честного сравнения intrusive-списка без snapshot
нужно сначала определить удаление, повторное добавление, prepend, вложенный emit и once.

## Проверка lifecycle и совместимости

Второй вариант проходит 116 тестов EventSignal (один пропущен), девять существующих GC-сценариев, сборку забытого
графа из трёх сигналов, сборку источника с живым владельцем зависимости/триггера и контроль доставки живому владельцу.
Явный dispose без нативного WeakRef проходит. Строгие проверки сохраняют 36 существующих диагностик библиотеки без
добавлений; потребители declarations в CommonJS/NodeNext/Bundler проходят. Полный Jest: 403 проходят, 14 ранее
зафиксированных падений, один пропущен, шесть todo. Эти падения остаются в наборе тестов emitter.

`eventName` публикует слабый адрес совместимости только при чтении. Обычные динамические зависимости и `deps: [source$]`
используют прямые каналы. `deps: [{ eventName: source$.eventName }]` разрешает этот адрес. У неизвестных произвольных
имён нет производящего сигнала, и они остаются инертными. Тестовые/отладочные экспорты `__test__get_*Emitter` теперь
возвращают замороженные представления диагностики только для чтения (`listeners`, `listenerCount`, `hasListener`,
`eventNames`), а не изменяемые общие шины. Перечисление охватывает только опубликованные адреса, не все сигналы.

Общие группы часов хранят слабые callbacks доставки каналу и слабые операции отключения; группировка таймеров и
существующее расписание сохранены. Символы сигналов идентифицируют подписки без требования слабых символов.
Исторический код таймеров и React не перемещался: новый helper содержит новую реализацию хранилищ и связей.

## Ограничения и дальнейшая работа

Для гарантий слабого владения нужен нативный WeakRef. FinalizationRegistry обеспечивает отложенную внешнюю очистку,
а не срок или замену dispose. Без финализации мёртвые слабые адреса можно удалять при поиске, но метаданные таймеров/
внешних регистраций могут сохраняться до явной очистки. Без нативного WeakRef используйте dispose.
Пользовательские computations могут намеренно удерживать источники; возвращённые дескрипторы подписок удерживают
владельца. Незавершённые внешние Promise всё ещё могут удерживать сигнал до завершения.

Это одна локальная нагрузка V8/runtime. Она не покрывает браузеры, Bun, Deno, async-графы, все динамические циклы
или всю семантику уничтожения источника. Прототип списка не моделирует computations EventSignal, таймеры, React,
внешние источники, полный API EventEmitterX, контекст listener или несколько аргументов. Утверждений о памяти или
скорости полного ядра на списках нет. Этап 02 остаётся открытым для этих проверок lifecycle и runtime.
