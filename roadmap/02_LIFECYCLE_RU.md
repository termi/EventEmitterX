# 02 — Утечка памяти и завершение lifecycle

Приоритет P0. Известная проблема владельца воспроизведена для derived signals. Сигнал без зарегистрированных
удерживающих callbacks может собираться; утверждение «все экземпляры всегда текут» не следует из аудита. См. MEM-01,
MEM-02 и LIFE-01/LIFE-02 в [аудите](AUDIT_RU.md#подробные-замечания).

## Сначала глобальные каналы — статус реализации

Активная реализация в `dev` сохраняет все три глобальных канала EventEmitterX со слабым владением callbacks.
Альтернатива с каналами экземпляров реализована и оценена, затем сохранена отдельно вместо слияния.

- [x] Слабые регистрации зависимостей, подписчиков, событий источника, триггеров, AbortSignal и React component/RAF
  callbacks; живые сигналы владеют исходными callbacks.
- [x] Метаданные финализации содержат символы и операции отключения без ссылки на владельца. Явный dispose отменяет
  финализацию и немедленно освобождает ресурсы.
- [x] Ошибки конструктора, уже отменённые владельцы, агрегирование ошибок очистки и запрет возобновления
  закрытых/уничтоженных подписок.
- [x] Девять отдельных GC-сценариев, контроль с живым владельцем и fallback с явным dispose без нативного WeakRef.
- [x] После коммита первого варианта владельцем реализовать и оценить каналы экземпляров/прямые связи; сохранить
  эксперимент отдельно с тестами, обоснованием и измерениями.
- [ ] Вернуться к внедрению только при конкретной выгоде, превышающей измеренные затраты памяти; внедрение отложено
  и не является обязательным следующим шагом.

## Архитектурное решение — 2026-10-06

Оставляем первый вариант в `dev`. Оба варианта проходят свои GC-проверки, поэтому второй не демонстрирует
дополнительного исправления известной проблемы удержания. В измеренной нагрузке активные computed-сигналы с подписчиком
требуют примерно на 12,7% больше предельного прироста heap во втором варианте; диапазоны времени обновления полного
графа пересекаются. Локальное владение полезно архитектурно, но само по себе не оправдывает внедрение текущей реализации.

Эксперимент сохранён в `experiment/eventsignal-instance-channels`, коммит
`d17917f2518a7b3a0700131b2076a949fdb0ae89`, на основе первого варианта из коммита
`686c0d19603b447a8b31ead6552b705c60acafca`. Слияния или cherry-pick в `dev` не было.
[Сравнение](verification/SIGNAL_CHANNEL_COMPARISON_RU.md) и исходные замеры доступны здесь;
реализация, скрипт бенчмарка и дополнительные GC-тесты находятся в той ветке.

Возвращаться к компактному каналу экземпляра или backend на списке следует только с сохранением семантики подписок/
изменений и измеренной выгодой на характерных нагрузках. Сам прототип списка не доказывает улучшения полной
реализации EventSignal. Переносимость runtime, динамические циклы и семантика уничтожения источника остаются работой этапа 02.

Запуск: `pnpm test:signals:gc`; fallback: `node --expose-gc _dev/check_signal_lifecycle.cjs --without-weakref`.
GC-регрессия падает на исходниках первоначального HEAD и проходит после исправления. Все 114 тестов EventSignal
проходят (один пропущен); строгие проверки библиотеки и трёх режимов потребителей declarations теперь требуют ноль диагностик.
См. [актуальную проверку базы](verification/BASELINE_VERIFICATION_RU.md).

[Решение, альтернативы и гарантии](../changelogs/reasons/EventSignal_WEAK_NOTIFICATION_OWNERSHIP.md).

Нативный WeakRef позволяет сборку; FinalizationRegistry обеспечивает eventual removal записей без установленного срока.
Без этих возможностей требуется явный dispose. Внешние дескрипторы подписок намеренно владеют своим сигналом.
Выполняющаяся асинхронная работа может удерживать владельца до завершения внешнего Promise; существующие тесты dispose и
позднего завершения по-прежнему проходят. Проверка нескольких runtime, исчерпывающий анализ динамических циклов и
семантика уничтожения источника остаются открытыми: этап 02 не завершён.

## Исходный удерживающий путь

`module signalEventsEmitter → listener под symbol зависимости → derived._oneOfDepUpdated → derived (this) → computation/data/source`.

После удаления внешних ссылок на derived регистр продолжает держать callback и экземпляр. FinalizationRegistry не может
исправить этот путь: его callback выполняется после того, как объект станет доступен GC. Существующая финализация также
не является гарантированным destructor и не охватывает всю ресурсную очистку.

## Работа

- [ ] Построить карту сильных ссылок для dependency/subscriber/timer registries, sourceEmitter, AbortSignal, React
  component registry, requestAnimationFrame queue, deferred promises и error объектов.
- [ ] Выбрать weak notification design: callback регистра должен хранить WeakRef к экземпляру, а не closure с this;
  metadata финализации не должна содержать экземпляр или callback, возвращающий его. Объекты-ключи слабого хранилища
  могут быть переносимее Symbol-ключей.
- [ ] Не считать замену Object на Map исправлением: Map удерживает значения сильно. WeakMap с символом также требует
  проверки платформы и всех обратных ссылок.
- [ ] Развести автоматическую сборку забытых сигналов и детерминированную отмену ресурсов.
  Destructor/AbortSignal/Disposable остаются способом немедленной очистки; GC используется как страховка, а не таймер
  закрытия.
- [ ] Для сред без WeakRef определить честный fallback и документированный уровень гарантий; fake WeakRef с сильным
  полем не обеспечивает автоматическое освобождение.
- [ ] Сделать destructor/dispose и unsubscribe идемпотентными. Определить suspend/resume после закрытия и очистку после
  уничтожения источника.
- [ ] Гарантировать очистку остальных ресурсов при исключении пользовательского cleanup/onDestroy; выбрать
  агрегирование/сообщение ошибок. Проверить constructor-failure и уже aborted signal.
- [ ] Проверить, что поздний async resolve/reject не оживляет уничтоженный сигнал, не уведомляет подписчиков и завершает
  ожидающие Promise согласно контракту.
- [ ] Добавить доступную в тестах диагностику числа активных связей, не создающую новых сильных ссылок на сигналы. Не
  подсчитывать Symbol events через текущий eventNames().

## Проверки и завершение

Детерминированные тесты: explicit cleanup, double cleanup, exception cleanup, abort до/после подписки, уничтожение во
время вычисления, таймеры/RAF, dynamic deps. GC suite: отдельный процесс с expose-gc, границы event loop, WeakRef и heap
retaining paths; ограниченный GC-прогон сам по себе может быть нестабилен, поэтому сверять со структурой графа.

Критерий P0: без внешнего владельца и без намеренно удерживающей пользовательской подписки глобальные registry callbacks
не удерживают derived signal; серии создания/удаления не накапливают связи. При explicit destructor ресурсы
освобождаются сразу и ровно один раз. Решение не ломает ленивость и доставку уведомлений.
