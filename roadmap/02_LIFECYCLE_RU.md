# 02 — Утечка памяти и завершение lifecycle

Приоритет P0. Известная проблема владельца воспроизведена для derived signals. Сигнал без зарегистрированных
удерживающих callbacks может собираться; утверждение «все экземпляры всегда текут» не следует из аудита. См. MEM-01,
MEM-02 и LIFE-01/LIFE-02 в [аудите](AUDIT_RU.md#подробные-замечания).

## Удерживающий путь

`module signalEventsEmitter → listener под symbol зависимости → derived._oneOfDepUpdated → derived (this) → computation/data/source`.

После удаления внешних ссылок на derived регистр продолжает держать callback и экземпляр. FinalizationRegistry не может
исправить этот путь: его callback выполняется после того, как объект станет доступен GC. Существующая финализация также
не является гарантированным destructor и не охватывает всю ресурсную очистку.

## Работа

- [ ] Построить карту сильных ссылок для dependency/subscriber/timer registries, sourceEmitter, AbortSignal, React
  component registry, requestAnimationFrame queue, deferred promises и error объектов.
- [ ] Выбрать weak notification design: callback регистра должен хранить WeakRef к экземпляру, а не closure с this;
  metadata финализации не должна содержать экземпляр или callback, возвращающий его. Объекты-ключи слабого хранилища
  могут быть переносимее Symbol-ключей.
- [ ] Не считать замену Object на Map исправлением: Map удерживает значения сильно. WeakMap с символом также требует
  проверки платформы и всех обратных ссылок.
- [ ] Развести автоматическую сборку забытых сигналов и детерминированную отмену ресурсов.
  Destructor/AbortSignal/Disposable остаются способом немедленной очистки; GC используется как страховка, а не таймер
  закрытия.
- [ ] Для сред без WeakRef определить честный fallback и документированный уровень гарантий; fake WeakRef с сильным
  полем не обеспечивает автоматическое освобождение.
- [ ] Сделать destructor/dispose и unsubscribe идемпотентными. Определить suspend/resume после закрытия и очистку после
  уничтожения источника.
- [ ] Гарантировать очистку остальных ресурсов при исключении пользовательского cleanup/onDestroy; выбрать
  агрегирование/сообщение ошибок. Проверить constructor-failure и уже aborted signal.
- [ ] Проверить, что поздний async resolve/reject не оживляет уничтоженный сигнал, не уведомляет подписчиков и завершает
  ожидающие Promise согласно контракту.
- [ ] Добавить доступную в тестах диагностику числа активных связей, не создающую новых сильных ссылок на сигналы. Не
  подсчитывать Symbol events через текущий eventNames().

## Проверки и завершение

Детерминированные тесты: explicit cleanup, double cleanup, exception cleanup, abort до/после подписки, уничтожение во
время вычисления, таймеры/RAF, dynamic deps. GC suite: отдельный процесс с expose-gc, границы event loop, WeakRef и heap
retaining paths; ограниченный GC-прогон сам по себе может быть нестабилен, поэтому сверять со структурой графа.

Критерий P0: без внешнего владельца и без намеренно удерживающей пользовательской подписки глобальные registry callbacks
не удерживают derived signal; серии создания/удаления не накапливают связи. При explicit destructor ресурсы
освобождаются сразу и ровно один раз. Решение не ломает ленивость и доставку уведомлений.
